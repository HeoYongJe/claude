# Design Guide — nike 프로젝트

> 이 문서는 이 프로젝트의 디자인 기준이다.
> 모든 화면과 컴포넌트는 이 문서를 먼저 읽고 따른다. 규칙과 어긋나면 만들기 전에 멈추고 물어본다.

## 1. Overview
- 성격: **포트폴리오용 비주얼 케이스스터디** (실제 서비스 아님, 데이터 없음)
- 컨셉: 나이키 브랜드를 소재로 한 **가상 캠페인/컨셉 랜딩 페이지** — 2021년식 jQuery 클론 사이트(구버전)를
  대체하는 완전히 새 디자인. "나이키라면 이런 캠페인 페이지를 만들었을 것 같다"는 톤.
- 브랜드명·워드마크는 나이키를 그대로 쓰되(이름 새로 짓지 않음), **스우시 로고 이미지 자산은 복제하지 않는다**
  (상표 이미지 그대로 베끼는 건 피하고, 워드마크는 타이포그래피로 직접 구현).
- 제품 비주얼: 지금은 **추상 그래픽(그라데이션·도형)**으로 채움. 실제 신발 사진/목업은 **사용자가 나중에 직접
  구해서 교체**(코드에 플레이스홀더 교체 지점을 명확히 주석으로 남길 것).
- 구성(원페이지): 히어로 → 매니페스토(짧은 선언문) → 제품 쇼케이스(스크롤 인터랙션) → 기능 하이라이트 →
  룩북 갤러리 → CTA(드롭 알림 신청, 실제 전송 없음) → 푸터

## 2. Colors
`css/style.css`의 `:root` 토큰이 단일 소스.

| 역할 | 토큰 | 값 |
|---|---|---|
| Ink(기본 배경, 히어로/CTA) | `--ink` | `#0A0A0A` |
| Ink 2(다음 톤, 카드 등) | `--ink2` | `#171717` |
| Paper(밝은 섹션 배경) | `--paper` | `#FFFFFF` |
| Paper muted(연한 회색 섹션) | `--paper2` | `#F5F5F5` |
| 포인트(액센트, CTA·하이라이트) | `--volt` | `#D7FF3E` |
| 본문(밝은 배경 위) | `--text` | `#111111` |
| 보조 텍스트(밝은 배경) | `--muted` | `#6B6B6B` |
| 본문(어두운 배경 위) | `--text-on-dark` | `#F5F5F5` |
| 보조 텍스트(어두운 배경) | `--muted-on-dark` | `#9A9A9A` |
| 경계선(밝은 배경) | `--border` | `#E6E6E6` |

- **흑백 대비가 기본 언어**: 섹션 단위로 완전한 블랙 또는 완전한 화이트를 쓰고, 중간 회색 배경은 최소화.
- **Volt(네온 옐로우그린)는 CTA·강조 한 곳에만** — 남용 금지(포인트 색이 희석되면 효과 없음).
- 컬러 사진/목업을 나중에 넣을 때도 이 톤(고대비 흑백 + volt 포인트)에서 크게 벗어나지 않게.

## 3. Typography
- **디스플레이(헤드라인)**: `Oswald`(Google Fonts, condensed bold) — 나이키 특유의 압축된 임팩트 서체 톤을
  웹폰트로 근사. 전부 대문자 + 넓은 letter-spacing 금지(오히려 타이트하게, -0.01~-0.02em).
- **본문**: `Pretendard`(한국어) — 다른 프로젝트와 동일 소스, 로딩 중복 없음.
- H1(히어로) 96px / 800 / line-height 0.95 (모바일 56px)
- H2(섹션 제목) 56px / 700 / line-height 1.0 (모바일 36px)
- 본문 16–18px / Pretendard Regular~600 / line-height 1.6
- 라벨/키커 13px / 700 / letter-spacing .08em / 대문자

## 4. Layout & Spacing
- 8px 그리드. 콘텐츠 최대 너비 1200px, 좌우 여백 24px(모바일 20px).
- 섹션은 **풀블리드(배경은 뷰포트 전체)** + 내부 콘텐츠만 1200px 정렬.
- 섹션 간 경계는 색 대비(흑/백 전환)로 구분 — 카드 테두리·그림자 남용 금지.

## 5. Motion
> **2026-10-19 1차**: "가뿐처럼 절제된 톤"이 아니라 화려하고 인터랙션이 강한 톤으로(사용자 지시). 커스텀 커서·
> 마그네틱 버튼·3D 틸트를 추가했으나 → **사용자 피드백: "살짝 과함, 인터랙션을 다 때려넣은 느낌. 원한 건 디테일보다
> 전체적인 화려함 — 큼직큼직하고 스크롤링에 따른 변화."** 즉 마우스 정밀도에 의존하는 "디테일 레이어"를 여러 개
> 겹치는 게 아니라, **스크롤에 반응해 화면 전체가 크게 움직이는 적은 수의 임팩트 있는 연출**을 원함.
>
> **2026-10-19 2차(현재 방향)**: 커스텀 커서·마그네틱 버튼·3D 틸트 **제거**. 대신 스크롤 스크러빙 기반의
> 큰 전환 효과에 집중.

- 스크롤 등장: 아래→위 페이드업(`opacity 0→1, translateY 40→0`), `IntersectionObserver` 1회 트리거(기본 베이스는 유지).
- **스크럽 스무딩(2026-10-19 1차, "효과가 더 부드러웠으면" 피드백):** 히어로 줌아웃·매니페스토 핀드줌·쇼케이스 비주얼
  스크럽 전부, 실제 `scrollY`를 바로 쓰지 않고 **lerp로 보간한 `smoothY`**를 공통으로 사용(가뿐 히어로 패럴럭스의
  lerp(0.09)와 동일 패턴). 계산 기준도 `getBoundingClientRect`(매 프레임 레이아웃 재계산 필요) 대신
  `offsetTop`/`offsetHeight`를 `resize`에 한 번만 캐시해두는 방식으로 바꿔 성능도 더 가벼워짐.
  ⚠️ **2차(같은 날, "섹션 전환·폰트 애니메이션이 딱딱 끊김" 추가 피드백):** lerp(0.085)만으론 부족 — 원인 둘 더 찾음:
  ①`.grain`(필름 질감 오버레이)의 `mix-blend-mode: overlay`가, 그 아래 레이어가 매 프레임 스크럽으로 바뀔 때마다
  블렌드 영역 전체 재합성을 유발해 스크롤 중 프레임이 끊겼음 → blend-mode 제거(opacity만으로 유사 효과 유지).
  ②lerp 계수를 0.085→**0.06**으로 낮춤(더 천천히 따라가게) — 마우스 휠처럼 값이 듬성듬성 들어오는 입력에서도
  개별 틱이 뭉개져 보이도록. ③스크럽 대상 요소(`.hero__inner`, `.manifesto__text`, 쇼케이스 SVG)에
  `backface-visibility: hidden` 추가해 GPU 레이어 합성을 더 안정적으로(폰트 서브픽셀 흔들림 완화 목적).
- **히어로 키네틱 타이포**: "NIKE" 4글자를 개별 `span`으로 쪼개 글자마다 다른 지연으로 scale+rotate+blur-in(유지).
- **히어로 스크롤 줌아웃(유지)**: 스크롤을 시작하면(0~1 viewport height 구간) 히어로 콘텐츠가 `scale` 커지면서
  `opacity` 빠지는 줌 통과 전환. `hero-wrap`(200vh)이 스크롤 공간을 주고 `.hero`는 그 구간만 sticky.
  ⚠️ **2026-10-20 시행착오**: "섹션 전환이 밋밋하다"는 피드백을 "다음 섹션이 이전 섹션 전체를 덮어야 한다"로
  잘못 해석해서, 한때 `.hero`를 바운드 없는 sticky(영구 고정)로 바꾸고 `.manifesto`가 전체를 덮어 올라오게
  만든 적이 있었음 → **"그 인터랙션(줌아웃) 좋았는데 왜 뺐냐, 전체를 덮으라는 게 아니라 배경만 attachment
  느낌을 달라는 거였다"는 피드백으로 되돌림.** 줌아웃은 그대로 복원하고, 실제 요청은 아래 "배경 패럴럭스"로 해결.
- **배경 패럴럭스("background-attachment" 느낌, 2026-10-20):** 섹션 전체가 아니라 **배경 레이어만** 콘텐츠와
  다른 속도로 움직여서 전환에 깊이감을 줌 — 전체를 덮는 과장된 연출이 아니라 은은한 터치.
  - `.manifesto__bg`/`.showcase__bg`: 가뿐 히어로 패럴럭스와 동일한 공식 `translateY(-(요소중심−뷰포트중심)*speed)`를
    `data-speed`(각각 0.15 / 0.2)로 적용. 이 두 섹션은 보통 문서 흐름으로 스크롤되므로(내부에 sticky 핀/비주얼만
    있고 섹션 자체는 sticky 아님) 뷰포트 안에서 위치가 바뀌어 이 공식이 정상 작동함(실측: scrollY 1400에서
    `.manifesto__bg`가 `translateY(-7.6px)`로 변함 — 확인됨).
    ⚠️ **버그(2026-10-20, 사용자가 스크린샷으로 지적):** 처음엔 `.manifesto__bg`에 직접 `inset:-10%`만 주고
    클리핑을 안 했는데(섹션 자체에 `overflow:hidden`을 주면 형제인 `.manifesto__pin`의 sticky가 깨져서
    일부러 뺐었음), 그 결과 **매니페스토가 아직 뷰포트에 들어오기도 전인데 배경(-10% 위로 확장 + 패럴럭스
    오프셋)이 히어로 영역까지 새어나와 겹쳐 보이는 가로 이음새**가 생겼음(실측: `manifestoRect.top=950`로
    아직 안 보여야 하는데 `mbgRect.top=557`로 이미 보이고 있었음). **`.manifesto__bgclip`/`.showcase__bgclip`
    이라는 전용 래퍼를 배경 바로 위에 추가**해서 `overflow:hidden`은 그 래퍼에만 주고(배경의 형제가 아니라
    배경만의 부모), sticky 요소(`.manifesto__pin`/`.showcase__visual`)는 그 래퍼 **밖의 형제**로 유지해
    sticky를 안 깨뜨리면서 배경만 섹션 경계 안에 가둠.
  - `.hero__bg`: `.hero` 자체가 sticky로 고정돼 있어 뷰포트 기준 위치가 안 바뀌므로 같은 공식이 성립하지 않음
    (실측 결과 `translateY(0px)` 고정 — 패럴럭스 없음을 직접 확인하고 교체). 대신 **히어로 progress에 직접
    바인딩해 배경을 전경보다 훨씬 느리게 확대**(배경 `scale(1→1.15)` vs 전경 `scale(1→1.9)`) — "배경은 거의
    제자리, 콘텐츠만 그 위를 빠르게 지나간다"는 동일한 체감을 다른 방식으로 구현.
- **매니페스토 핀드 줌텍스트**: 섹션을 2.2배 높이(`220vh`)로 늘리고 텍스트를 `sticky`로 중앙 고정, 그 구간 스크롤
  진행률에 따라 텍스트가 `scale(0.5→1.15)`로 커지며 등장 — 큰 스크롤텔링 연출(Awwwards에서 흔한 "핀 텍스트 줌" 기법).
  **2026-10-20 조정**: 같은 "핸드오프가 급작스럽다" 문제가 2→3 전환(매니페스토→쇼케이스)에도 있었음 — progress가
  sticky 해제 시점과 정확히 동시에 1.0에 도달해 "확대 완료 = 곧바로 스크롤아웃"이었음. **progress 계산을
  `range*0.75`로 나눠 75% 지점에서 이미 확대 완료**시키고, 나머지 25% 구간은 완전히 확대된 채로 "멈춰 있다가"
  쇼케이스(검정)가 자연스럽게 덮어오도록 호흡을 줌.
- **스크롤 스크러빙(제품 쇼케이스)**: 1회성 reveal이 아니라, 섹션 스크롤 진행률(0~1)에 실시간으로 바인딩해서 비주얼이
  계속 회전(`rotate`)·확대(`scale`)·글로우 강도가 변함 — Apple 제품 페이지처럼 "스크롤이 곧 애니메이션 타임라인"(유지).
- **스펙 숫자**: 뷰포트 진입 시 `scale(0.3)+blur`에서 오버슈트 있는 큰 팝업(elastic) + 0→실제값 카운트업. 작은
  페이드가 아니라 "쾅" 하고 등장하는 느낌.
- **룩북 타일**: 뷰포트 진입 시 `clip-path`가 한쪽에서 다른 쪽으로 크게 와이프되며 열림(단순 fade 아님).
- **마퀴 텍스트 밴드**: 매니페스토~쇼케이스 사이에 큰 글씨가 좌→우 무한 스크롤되는 띠(유지, "JUST MOVE —" 반복).
  장식용(`pointer-events:none`, `aria-hidden`), 가뿐의 인기 여행지 티커와 같은 구현 패턴(세트 2번 렌더).
- **그레인 텍스처**: 어두운 섹션에 은은한 필름 그레인 오버레이(유지).
- `prefers-reduced-motion: reduce`면 **위 전부** 즉시 최종 상태로(스크러빙·핀드줌·줌아웃·카운트업·와이프 전부
  비활성화/즉시 완료 상태, 마퀴는 정지) — 기존 프로젝트들과 동일 규칙.
- **히어로 블러 인/아웃(2026-10-22 추가):** "사이트가 열리면 타이포가 흐림 상태에서 선명해졌다가, 스크롤하면
  다시 흐려지며 다음 섹션으로 넘어간다"는 요청 — 입장과 퇴장 두 축으로 구현.
  - **입장(1회성)**: 기존 `[data-reveal]` 공통 페이드업(opacity+translateY)에 `.hero [data-reveal]`
    스코프로 `filter: blur(14px) → blur(0)`를 추가(전환 `.9s`, 다른 둘보다 살짝 느리게 잡아 "샤악"하고
    블러가 걷히는 임팩트). kicker·NIKE·tagline·sub 네 요소가 기존 `nth-child` 지연값 그대로 순차 등장
    — NIKE 단어 자체는 이미 글자별 `letterIn` 키프레임에서 별도로 blur(6px)→0을 쓰고 있어 이중으로
    겹쳐 더 또렷한 블러 임팩트를 냄.
  - **퇴장(스크롤 연속)**: 기존 히어로 스크롤 줌아웃(`js main.js`의 `heroInner` scale 1→1.9, opacity 1→0,
    같은 progress 0→1 구간)에 `heroInner.style.filter = blur(progress*14px)`를 같은 값으로 추가 —
    입장 때 쓴 블러 세기(14px)와 동일하게 맞춰 왕복이 대칭으로 느껴지게 함.
  - `prefers-reduced-motion`에서는 `[data-reveal]`·`.hero__inner`에 `filter: none !important`를 추가해
    블러가 중간에 멈춰 보이는 일이 없게 함(위 공통 규칙에 포함).
- **히어로→매니페스토 전환 "죽은 구간" 수정(2026-10-29):** "타이틀이 사라지고 섹션2로 넘어갈 때 여백이
  너무 많이 남아 미완성 같다" 피드백 — 원인은 히어로 opacity가 `1 - progress*1.6`이라 핀 구간(스크롤
  가능 범위)의 62.5% 지점에서 이미 완전히 투명해지는데, 핀 자체는 100%까지 유지돼 나머지 37.5%
  (`hero-wrap 200vh` 기준 약 75vh)는 콘텐츠 없이 어두운 화면만 스크롤되는 구간이었음. `opacity`를
  `1 - progress`로 바꿔 range 전체를 다 쓰게 해 핀이 풀리는 정확한 순간에 텍스트가 사라지도록 동기화.
  곁들여 `hero-wrap`을 200vh→180vh로 살짝 줄이고, 매니페스토 쪽도 초기 scale 0.5→0.65·opacity 램프
  ×2.5→×3로 더 빨리·더 큰 크기로 또렷해지게 다듬어 핸드오프 체감을 타이트하게 만듦.

      `scale(1.14)`로 커질 때 위아래로 튀어나온 부분(라운드 모서리 포함)이 그대로 잘려 나가 직각처럼
      보였던 것. `.lookbook__viewport`에 확대분을 충분히 덮는 세로 padding(44px~64px)을 줘서 애초에
      잘릴 내용이 없게 해결 — 모든 슬라이드가 항상 완전한 둥근 사각형(같은 박스, scale만 다름)으로
      보이므로 "모양이 안 맞다"는 지적도 같이 해소됨.
    - **버그 3 — 마우스 휠로 페이지 스크롤할 때 슬라이드가 반응하던 것**: 원인은 `overflow-x:auto`인
      요소 위에서 마우스 휠(세로 입력)을 돌리면 일부 브라우저가 그 세로 입력을 가로 스크롤로 떠넘기는
      동작 — 페이지를 스크롤하려던 휠 입력이 슬라이더 내부 스크롤 위치를 멋대로 바꿨음. 새 구조는
      뷰포트가 `overflow-x:hidden`일 뿐 스크롤 가능한 축 자체가 없어(위치는 전부 transform으로만 바뀜)
      휠이 항상 페이지 스크롤로만 쓰임 — 구조적으로 재발 불가능.
    - **가운데-나머지 대비 강화 + 화려한 전환**: 거리 기반 연속 보간(2차) 대신 활성(`is-active`)/
      인접(`is-near`)/비활성(기본) 3단계로 나눠 scale(1.14 / .92 / .78)·opacity·blur·그림자 차이를
      뚜렷하게 키우고, cubic-bezier(`.16,1,.3,1`, "expo-out") 이징으로 전환에 탄력을 줌.
    - **마우스 드래그 + 터치 스와이프 통합**: 2차의 `mousedown`/`mousemove`(마우스 전용) 대신 Pointer
      Events로 다시 구현 — 마우스·터치·펜이 전부 같은 코드 경로를 타므로 터치 스와이프도 별도 분기 없이
      동작. 드래그 중 `transform`을 1:1로 따라가다가(전환 애니메이션 꺼짐), 손을 떼면 이동 거리로 몇
      칸 넘어갔는지 계산해 가장 가까운 인덱스로 애니메이션과 함께 스냅.

    - **"중앙 정렬인데 한쪽만 비어 보이던" 문제의 정체**: 3차 수식은 실측 오차 0.03px로 수학적으로

      (+부수 효과로 활성이 작아진 만큼 이웃과의 겹침도 줄어 그림자 버그와 동시에 해결).
    - 슬라이드 사이 `gap`도 24px→32px(모바일 16px→20px)로 넓혀 스케일 전환 중에도 여유를 더 줌.

      없어짐(루프이므로 항상 눌림) — 5차에서 버그의 근원이었던 "`offsetLeft` 실측값에 의존하는 로직"
      (3~6차에 걸쳐 센터링 오차·캐시 타이밍 문제의 원인이 됐던 패턴) 자체가 이번 구조엔 아예 없음.
    - **드래그 인터랙션 단순화**: 이전 버전은 드래그 중 트랙을 1:1로 끌리는 대로 따라가게 했지만, 스택
      구조는 "연속된 오프셋"이라는 개념이 없어(각 랭크는 이산적인 고정 위치) 1:1 추종이 불가능 —
      일정 거리(50px) 이상 끌고 놓으면 `next()`/`prev()`를 한 번 호출하는 "스와이프 제스처"로 단순화.
    - 중간 데스크톱 폭(900~1300px)에서 타이틀 칸(440px)과 스택이 겹치지 않도록 카드 크기·오프셋을
      ~22% 축소하는 보조 브레이크포인트를 추가. 모바일(≤900px)은 폭이 더 좁아 3장 전부 보여주면
      서로 거의 다 겹쳐버리므로 메인+다음 2장만 보이게 축소(그 이상은 전부 화면 밖 대기).
  - **8차(같은 날): "스택 방식 자체는 나쁘지 않은데, 타이틀하고 카드 더미 사이 빈 공간이 동그라미
    친 만큼 너무 멀다"(스크린샷에 빈 공간을 원으로 표시 + 왼쪽을 가리키는 화살표) — rank0·1을
    타이틀 쪽으로 당겨 간격을 좁힘:**
    - **간격이 벌어졌던 원인**: 7차에서 각 랭크의 `right`(뷰포트 오른쪽 끝 기준 오프셋)를 고정 px로
      잡을 때, 넓은 화면(사용자 스크린샷은 와이드 데스크톱)에서는 `.lookbook__slider`가 화면 오른쪽
      끝까지 쭉 넓어지는데 rank0는 여전히 그 오른쪽 끝에서 고정된 380px 거리에만 머물러 있어서,
      "타이틀 칸이 끝나는 지점"과 "rank0가 시작하는 지점" 사이에 뷰포트가 넓어질수록 같이 커지는
      죽은 공간이 생겼던 것 — 6차에서 고쳤던 "풀블리드인데 콘텐츠가 가운데 좁게 몰려 보인다"류
      버그가 이번엔 스택 컴포넌트 내부에서 다른 모습으로 재발한 셈.
    - **1차 시도와 버그**: rank0 `right`를 380→640px로 키워(= 뷰포트 오른쪽 끝에서 더 멀리, 즉
      타이틀 쪽으로 더 깊이) 간격을 크게 줄였는데, `getBoundingClientRect()`로 실측해보니 카드
      왼쪽 끝(x≈685, 1800px 뷰포트 기준)이 타이틀 칸의 오른쪽 끝(x≈740)보다 더 왼쪽까지 들어와
      있었음 — `.lookbook__slider`는 `position:relative`인 스택의 포지셔닝 기준점일 뿐, absolute
      자식이 그 박스의 "왼쪽 경계" 밖으로 넘어가는 걸 막아주지 않는다는 점을 간과함(각 랭크는
      `right` 값만으로 위치가 정해지고, `left` 쪽은 전혀 제약이 없어 음수든 뭐든 자유롭게 계산됨).
    - **최종 수정**: "카드 왼쪽 끝이 `.lookbook__slider`의 실제 왼쪽 경계(= 헤드 폭 440px + flex
      gap 56px + 레이아웃 왼쪽 패딩)보다 왼쪽으로 가면 안 된다"는 제약을 식으로 세우고(
      `sliderRight - right - width >= sliderLeft`) 역산해 rank0 `right`를 640→**480px**로 낮춤 —
      1800px 뷰포트 기준 실측으로 안전마진 약 48px를 두고 확정(`rank0.left - slider.left ≈ 48.7px`).
      rank1도 같은 비율로 290→**240px**로 같이 당겨 rank0와의 겹침(fan 느낌)을 유지. rank2는
      7차 값(`right:40px`, 우측 끝에서 거의 그대로)을 유지해 "화면 우측 끝까지 채운다"는 7차 요청도
      계속 지킴. 결과적으로 타이틀-카드 간격은 기존 대비 ~370px 줄어들면서도(약 420px → ~50px급)
      타이틀 칸을 침범하지 않는 안전한 값으로 수렴.
    - **900~1300px 중간 구간은 이번엔 그대로 둠**: 같은 비율로 당기면 그 구간 하한(901px)에서는
      애초에 슬라이더 폭 자체가 좁아(카드 3장 폭 합보다 좁음) 타이틀 칸 침범이 더 심해지는 걸
      계산으로 확인(이건 8차 이전부터 있던 잠재 버그지만 이번에 더 당기면 악화됨) — 사용자가 이번에
      지적한 스크린샷은 넓은 데스크톱 폭 기준이었고 이 중간 구간에 대한 피드백은 아직 없어서, 무리하게
      같이 당기지 않고 7차 값을 그대로 유지(regression 방지가 우선). 이 구간을 더 좁히려면 헤드 폭
      자체를 줄이거나 카드 크기를 뷰포트 단위(vw)로 반응형화하는 추가 작업이 필요 — 다음 피드백이
      오면 그때 손볼 것.
  - **9차(같은 날): "2560px 화면인데 바뀐 게 하나도 없다 — 여전히 슬라이드가 우측에 짱박혀있다" —
    `right` 기준 포지셔닝 자체를 폐기하고 `left` 기준으로 전환(해상도 무관하게 동작하도록):**
    - **8차 수정이 안 먹힌 진짜 원인**: 8차는 1800px 뷰포트에서 실측하고 튜닝한 값이었는데, rank0·1을
      `right`(뷰포트 오른쪽 끝 기준 고정 px)로 위치시키는 방식 자체가 화면이 넓어질수록 효과가
      희석되는 구조였음 — `.lookbook__layout`의 `padding-left`가 `(100vw-1200px)/2`라 뷰포트가
      넓어질수록 **타이틀 칸 자체가 오른쪽으로 밀리는데**, rank0는 여전히 "뷰포트 오른쪽 끝에서
      고정 480px"에만 머물러 있어서 타이틀이 밀려오는 속도를 못 따라감 — 1800px에서 측정한 48px
      간격이 2560px에서는 다시 벌어짐(계산상 2560px에서 타이틀-카드 간격이 8차 이전 수준인 약
      370px대로 복귀). 6차에서 고쳤던 "풀블리드인데 콘텐츠가 가운데 좁게 몰려 보인다" 버그의 사촌뻘
      — 둘 다 "뷰포트 폭에 비례해서 커지는 여백을 고정 px 값으로는 못 따라잡는다"는 같은 근본 원인.
    - **진짜 해법 — 기준점을 "뷰포트 오른쪽 끝"에서 "타이틀이 끝나는 지점"으로 바꿈**: `right` 대신
      `left`를 쓰면 좌표 기준이 `.lookbook__slider`(타이틀 칸 바로 다음, flex 레이아웃이 알아서
      타이틀 폭+패딩을 반영해 위치를 계산해주는 박스)의 **왼쪽** 경계가 되고, 이 경계는 애초에 "타이틀
      칸이 끝나는 지점"과 정확히 같음 — `left: 48px`라고 쓰면 해상도가 얼마든(1800이든 2560이든
      4K든) 타이틀로부터 항상 정확히 48px 떨어진 위치가 보장됨(flex 레이아웃이 그 좌표계 자체를
      반응형으로 관리해주기 때문, 실측으로 2560px에서도 1800px와 동일하게 `gapFromSlider≈48px`
      확인). rank0(`left:48px`)·rank1(`left:378px`, rank0와 겹쳐 보이도록 조정)을 이 방식으로 교체.
    - **우측 끝 플러시(rank2)는 수식만 등가 변환**: `right:40px`(뷰포트 오른쪽 끝에서 40px, 슬라이더가
      풀블리드라 이 기준은 처음부터 해상도 무관하게 잘 동작했음)를 `left: calc(100% - 250px)`
      (=위드스 210px + 40px를 뺀 지점)로 바꿔 **같은 동작을 `left` 하나로 통일** — "우측 끝까지
      채운다"는 6~7차 요청을 그대로 유지하면서 랭크 전환 애니메이션도 끊기지 않게 함(아래 항목 참고).
    - **왜 `left` 하나로 통일해야 했는지(버그 발견 과정)**: 처음엔 rank0·1만 `left`로, rank2·대기
      랭크는 `right`를 유지하는 "섞어 쓰기"를 시도했는데, 한 슬라이드가 `next()`로 rank1(`left`
      사용)에서 rank2(`right` 사용)로 넘어갈 때 `left` 값이 구체적인 px에서 `auto`로(또는 그
      반대로) 바뀌는 상황이 생김 — CSS는 `auto`를 경유하는 transition을 보간하지 못해 애니메이션이
      튀어버림(부드럽게 움직이다 뚝 끊기는 버그). 모든 랭크가 `left`에 항상 구체적인 값을 갖도록
      통일해서 해결 — `transition` 목록에도 `left`를 추가(`right`도 혹시 몰라 같이 남겨둠, 모바일/
      중간 구간에서 실제로 쓰이므로).
    - **모바일(≤900px)·중간 구간(901~1300px) 호환성**: 이 두 구간은 여전히 `right`(vw 또는 px)로
      포지셔닝하는데, 기본 규칙이 이제 `left`를 명시적으로 지정하므로 **아무것도 안 하면 두 값이
      동시에 살아있는 상태**가 되고, CSS 스펙상 `left`·`right`·`width`가 전부 구체값이면 `left`가
      이김(=다른 두 구간에서 `right` 값이 통째로 무시되는 회귀 버그가 생길 뻔함) — 두 미디어쿼리의
      모든 랭크 규칙에 `left: auto;`를 명시적으로 추가해서 기본 규칙의 `left`를 지우고 `right`가
      의도대로 다시 적용되게 함. 1100px(중간 구간)·375px(모바일) 양쪽 다 레이아웃 정상 확인.
- **CTA**: volt 배경 또는 블랙+volt 텍스트, 이메일 입력(목업, 실제 전송 없음 — 제출 시 "신청 완료" 텍스트만 토글).
- **푸터**: 미니멀, 블랙.
